# 高負荷時のバッチ処理と更新頻度制御の方針

サーバー負荷に応じて流体更新を間引いたり、複数の無限水源をまとめて処理するための設計メモです。現行の挙動で使える設定と、今後の追加オプション案を整理します。

## 1. 現行の負荷平準化手段
- **更新間隔の手動調整**: `waterTickDelay` を 4–8 程度に上げることで、サーバーが重い間は流体更新頻度を下げられます。視覚的な遅延は出ますが、TPS が戻れば値を下げて即座に元のテンポに戻せます。
- **距離別の減速更新**: `advanced_flow_distances` と併用する距離別最適化では、距離 0–4 ブロックを毎 tick、5–16 を 2 tick ごと、17–32 を 4 tick ごと、33–64 を 8 tick ごと、65+ を 10 tick ごとに更新して負荷を平準化します。プレイヤーが 32 ブロック以内にいる場合は毎 tick 更新に戻るため、近距離の見た目は崩しません。

## 2. 負荷連動で更新頻度を自動調整する案
- **TPS 監視による間引き**: サーバー TPS や BFS キュー残量を監視し、しきい値を下回った tick だけ `waterTickDelay` を一時的に増やす。TPS が戻れば段階的に通常値へ戻す。
- **チャンク単位のスロットリング**: チャンクごとの更新コスト（処理済みノード数など）を計測し、重いチャンクには次の更新までの猶予 tick を積む。軽いチャンクは通常通りの頻度を維持する。
- **プレイヤー優先のフェイルセーフ**: プレイヤーが近いチャンクでは間引きを緩め、遠距離や無人チャンクから順に遅延させる。視覚破綻を避けつつバックログを解消できる。

## 3. 無限水源をまとめて処理するバッチ案
- **川・海のクラスタ集約**: 同一流体がチャンク境界をまたいで隣接する領域を一つのクラスタとして収集し、BFS をクラスタ単位で一度だけ実行する。クラスタ内では節点数に上限を設け、結果水位だけを各ブロックへ書き戻すことで「一括計算・個別反映」を実現する。
- **体積プリキャッシュ**: クラスタごとに総水量を計算し、流入・流出がなければそのまま共有キャッシュを使って処理をスキップする。チャンクロード時や大きな地形更新時だけキャッシュを破棄する。
- **部分更新の分割適用**: 1 tick でクラスタ全体を処理しきれない場合、チャンク境界や 16×16×16 のサブグリッドごとに分割し、N tick に分散して反映する。視覚的なずれを防ぐため、サブグリッド単位で連続 tick を割り当てる。

## 4. 高速シミュレーションと反映の二段階処理案
- **軽量プレビュー計算**: 本番の BFS より浅い深さ・低いノード上限で「プレビュー」シミュレーションを実行し、見込みの水位変化だけを記録する。プレビュー結果が小さい場合は本番処理をスキップし、変化が大きい場合だけ通常 BFS を走らせる。
- **サンプリング区間の高速化**: 連続した平坦面や水深が均一な水域では、高さを 1 カラムずつまとめて扱う「柱状サンプル」に置き換えてシミュレーションする。差分反映時にだけブロック粒度へ展開することで、平面水域のコストを下げる。
- **バックグラウンド適用**: 結果を書き戻すときは優先度キューに載せ、プレイヤーが視認できる領域から先に反映する。TPS が低下した tick はキュー処理数を減らし、高負荷時のスタッタを避ける。

## 5. 運用上の注意
- バッチ処理や間引きは「見た目の遅れ」を伴うため、デフォルトでは無効化し、設定で段階的に有効化できる形にする。
- 平均化や押し出し処理のロック順序を変えないよう注意し、クラスタ集約時も既存の排他制御を再利用する。
- 無限水源を一括処理しても、局所的な水位の上下はゲームプレイに影響するため、反映フェーズではチャンク境界の不連続を必ず補正する。
