# Stability regression fixes - 2026-03-19

## 今回直したこと
- `ParallelFluidTickManager` のチャンク並列グループを固定 4 群に変えて、8 近傍が同時に走らないようにした。
- `EnhancedFluidBFS` のクラスタ再配分を floor + 余り再配布へ変えて、水量補正を 1 点に押し込まないようにした。
- `AdaptiveTickScheduler` は近傍署名に loaded / empty / replaceable を含め、未ロード隣接があるときは安定キャッシュと長遅延を使わないようにした。
- `MixinFlowingFluid` の waterlog 特殊処理は、実際に移送したときだけ handled 扱いにし、`totalAmount < 8` の no-op 早期終了をやめた。
- `MixinWaterFluid` の蒸発は、同系 fluid が上にある水中列へ誤適用しないようにした。

## 原因
- 隣接チャンクを greedy coloring に任せると、未着色の隣接チャンクが同色へ入り得て、同一バッチで水を書き換える経路が残っていた。
- BFS の丸めを各ブロック単位で `Math.round` すると、クラスタ全体では差分がずれやすく、最後に 1 箇所補正すると水量破綻が起きやすかった。
- スケジューラの近傍キャッシュが「量だけ」で成立していて、未ロード隣接まで空気寄りに扱うと、流れるべき水まで安定と誤判定しやすかった。
- waterlog 特殊処理が「何も移していないのに handled=true」を返すことがあり、通常フローも止めてしまっていた。

## 今後避けたいこと
- ワールド書き込みを伴う並列グループは、局所最適な coloring よりも衝突しない固定分割を優先する。
- 流体総量を守る処理では、丸め誤差を最後に 1 ノードへ押し込まない。
- チャンク境界付近の安定化判定は、未ロード状態を「空気と同じ」とみなさない。
- waterlog や virtual fluid の特殊分岐では、「ブロックした」「実際に移送した」「通常処理へ戻す」を明確に分ける。
